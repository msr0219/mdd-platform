# 建模与运行指南

## 配置文件组织约定

全部菜单集中维护在 `meta/menus/main.json` 的 `menus` 数组中。新增入口追加到相应父菜单的 `children`，或作为独立应用追加到顶层；菜单编码在整个菜单树中唯一。

视图按应用模块分文件，同一应用的列表、表单及其他视图放在同一文件的 `views` 数组中：

| 视图文件 | 应用内容 |
| --- | --- |
| `meta/views/education.json` | 学生、课程等教学应用 |
| `meta/views/equipment.json` | 设备管理 |
| `meta/views/inventory.json` | 零件批次、库存流水 |
| `meta/views/production.json` | 生产工单、整机、装机零件、更换历史 |
| `meta/views/quality.json` | 不良处置、返工记录、质量检验与指标 |
| `meta/views/bom.json` | 产品BOM版本、零件明细、初装领料核销 |

视图编码在全部文件中唯一，不能把同一个视图复制到多个文件。新增独立应用时可增加对应的视图JSON；模型仍按模型分别保存，服务编排沿用 `meta/services/`。拆分视图文件不会改变视图编码和菜单路由。

## 1. 新增业务模块

以新增“教室”为例，创建 `meta/models/classroom.json`：

```json
{
  "model": {"code":"classroom","name":"教室","table":"t_classroom"},
  "fields": [
    {"code":"roomNo","name":"教室编号","type":"string","length":30,"required":true,"unique":true,"editable":true,"listable":true,"searchable":true},
    {"code":"capacity","name":"容量","type":"integer","min":1,"required":true,"editable":true,"listable":true,"searchable":true}
  ]
}
```

将下例 `views` 中的两个视图对象追加到 `meta/views/education.json` 的现有 `views` 数组中，保留已有学生、课程视图：

```json
{
  "views":[
    {
      "code":"classroom_list","name":"教室管理","type":"list","model":"classroom",
      "search":{"fields":[{"field":"roomNo","op":"like"}]},
      "table":{
        "columns":[{"field":"roomNo","title":"教室编号"},{"field":"capacity","title":"容量"}],
        "pagination":{"pageSize":20},
        "buttons":[
          {"code":"create","name":"新增","action":"openForm:classroom_form"},
          {"code":"edit","name":"编辑","action":"openForm:classroom_form","rowSelected":true},
          {"code":"delete","name":"删除","action":"service:classroom.delete","rowSelected":true,"confirm":"确定删除吗？"}
        ]
      }
    },
    {
      "code":"classroom_form","name":"教室","type":"form","model":"classroom",
      "fields":[{"field":"roomNo"},{"field":"capacity"}],
      "buttons":[
        {"code":"save","name":"保存","action":"service:classroom.create","success":{"close":true,"refresh":true,"message":"保存成功"}},
        {"code":"cancel","name":"取消","action":"close"}
      ]
    }
  ]
}
```

编辑 `meta/menus/main.json`，在 `education` 菜单的 `children` 数组中追加以下菜单对象，保留已有菜单：

```json
{"code":"classroom","name":"教室管理","view":"classroom_list","order":2}
```

在页面点击“热重载”，即可看到菜单并操作数据。也可调用 `meta.reload`。校验通过前配置不会生效；错误会带文件、路径、原因。菜单 code 在整个菜单树中必须唯一，视图和模型 code 在各自类别内唯一。不要直接复制需求文档里含重复菜单 code 的说明性样例。

## 2. 模型约定

- 字段类型：`string/text/integer/decimal/boolean/date/datetime/enum/ref`。
- `enum` 使用 `options: [{"value":"A","label":"选项 A"}]`；当前枚举值使用字符串。
- `ref` 使用 `"ref":"目标模型编码"`，保存时验证目标记录存在；反向查询使用 `source.related`。
- 时间格式：日期 `2026-11-10`，时间 `2026-11-10T09:30:00`，不附时区；当前业务 datetime 是本地日期时间。
- 每条记录自动附带 `id/version/created_by/created_at/updated_by/updated_at/deleted`。当前操作者取自服务端登录会话；初始化任务为 `system`。
- `idType` 支持 `auto/uuid/snowflake`，雪花策略仅面向当前单实例。
- 更新与删除必须提交 `id` 和当前 `version`，版本冲突后刷新并重新确认操作。
- `appendOnly:true` 禁止 update/delete/adjust/transition。状态单据与不可修改的历史流水分开建模。
- 自动 DDL 只建表、追加列及索引。已有数据的表不能直接追加没有回填方案的必填列。平台预检类型、长度、decimal 精度、必填约束和主键策略变化，发现漂移拒绝重载并保留旧快照，需要人工迁移。移除可空属性不删除已有列，但查询结果不再返回该属性。失败的数据库 DDL 仍可能已经留下新增列，但不会切换内存元模型。
- 唯一值由数据库约束保证，已软删除记录的唯一值仍被保留。

## 3. 事务服务

完整示例在 `meta/services/production.json`。一份服务至少包括 `code/name/params/steps`。`idempotencyKey` 必须指向显式声明的参数；本项目使用 `requestId`。服务默认开启事务，只支持 `onError:rollback`。

映射词汇：

| 配置 | 含义 |
| --- | --- |
| `"params.qty"` | 调用入参 |
| `"guards[0].result.version"` | 第一个前置检查读到的版本 |
| `"steps[0].result.id"` | 第一个步骤返回的主键 |
| `{"const":"GOOD"}` | 常量，避免与路径表达式混淆 |
| `{"negate":"params.qty"}` | 数值取负 |
| `{"add":["params.a","params.b"]}` | 加法 |
| `{"subtract":["params.a","params.b"]}` | 减法 |

守卫可以调用 read 并验证结果：

```json
{
  "call":"part_batch.read",
  "map":{"id":"params.batchId"},
  "condition":{"left":"result.qualityStatus","op":"eq","right":{"const":"GOOD"}},
  "message":"只能对良品库存领料"
}
```

后续库存调整必须使用该守卫结果中的 version，避免检查质量后发生并发修改却仍完成扣减。`adjust` 请求是 `{id,field,delta,version}`，只接受可编辑数值字段，调整后不能为负数。

声明 `idempotencyKey` 的业务服务通过请求编号防止重复执行。业务表单为每次操作生成独立 requestId，网络失败重试沿用原 requestId 和参数。服务编码与 requestId 构成唯一键；相同键改参返回 -32012。幂等记录不按短 TTL 自动清理，生产化时需要根据业务重试周期制定归档策略。

前端按钮 `map` 使用 `row.id`、`row.version`、`form.字段`、`search.字段`、`$requestId` 和 `{const:值}`。前端映射与后端服务映射的上下文不同。

### 3.1 用 Java 定制指定模型的 CRUD

模型字段、类型和约束继续在 `meta/models/` 中定义。需要在某次增删改查中执行专用 Java 逻辑时，编写继承 `ModelCrudHandler` 的 Spring 处理类，通过 `modelCode()` 绑定模型编码，只重写需要定制的方法。

项目在 `platform-server/src/main/java/com/platform/custom/StudentCrudHandler.java` 中注册了学生处理类：学生新增时去掉姓名两端空白，然后交给通用新增逻辑执行必填、类型、唯一性校验和保存。`examples/java/StudentCrudHandler.java` 为参考副本，主源码中的处理类随应用启动自动生效。

1. 在 IDEA 打开 `platform-server/src/main/java/com/platform/custom/StudentCrudHandler.java`，直接在该文件中定制学生逻辑。
2. 处理类带有 `@Component`，`modelCode()` 返回已存在的 `student`。一个模型只注册一个处理类；多个动作在同一个类中重写。为其他模型添加处理类时，使用新的 Java 类名及对应模型编码，文件路径与 `package` 保持一致；不要将参考副本注册为第二个学生处理类。
3. 编辑重写方法中的业务逻辑。此处将参数复制为局部对象，避免修改共享状态。

```java
package com.platform.custom;

import com.fasterxml.jackson.databind.JsonNode;
import com.fasterxml.jackson.databind.node.ObjectNode;
import com.platform.service.extension.ModelCrudContext;
import com.platform.service.extension.ModelCrudHandler;
import org.springframework.stereotype.Component;

@Component
public class StudentCrudHandler extends ModelCrudHandler {
    @Override
    public String modelCode() {
        return "student";
    }

    @Override
    public Object create(ModelCrudContext context, JsonNode params) {
        ObjectNode normalized = ((ObjectNode) params).deepCopy();
        if (normalized.path("name").isTextual()) {
            normalized.put("name", normalized.get("name").asText().strip());
        }
        return super.create(context, normalized);
    }
}
```

4. 停止 IDEA 中的后端，重新编译并运行 `PlatformApplication`；使用脚本运行时，停止后端后在项目根目录执行 `build.ps1`，再执行 `start.ps1`。Java 类修改需要编译和重启，点击“重载元模型”只处理 JSON。
5. 登录具有学生维护权限的账号，新增一个未使用的学号，姓名输入 `  张三  `。保存后的姓名应为 `张三`。也可用已登录会话调用 `student.create`：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "student.create",
  "params": {"studentNo": "JAVA-DEMO-001", "name": "  张三  "}
}
```

每次验收使用不同学号，避免已有唯一值影响结果。页面、JSONRPC 和 JSON 服务中的 `student.create` 调用都会进入同一个处理类；其他模型以及此类未重写的学生动作继续执行通用逻辑。模型 JSON 无需增加 Java 类名或绑定属性。

### 3.2 处理类调用规则

可重写的动作包括 `create`、`read`、`list`、`update`、`delete`、`batchCreate`、`batchDelete`、`adjust`、`transition`、`aggregate`、`related`，方法均使用 `(ModelCrudContext context, JsonNode params)` 参数并返回 `Object`。

| 写法 | 用途 |
| ---- | ---- |
| `super.create(context, params)` | 在重写的新增方法中继续执行通用新增；其他动作使用对应的 `super` 方法 |
| `context.proceed(params)` | 使用调整后的参数执行当前动作的通用实现，跳过当前处理类 |
| `context.proceed()` | 使用本次传入参数执行当前动作的通用实现 |
| `context.call("list", params)` | 调用当前模型的另一个动作，并经过其处理类 |
| `context.call("course", "list", params)` | 调用指定模型和动作，沿用本次元模型快照 |
| `context.modelCode()`、`context.action()` | 获取当前模型编码与动作 |
| `context.model()` | 获取模型定义副本，可供读取字段和配置 |

在 `create` 中调用 `context.call("create", params)` 会再次进入同一重写方法；保存应使用 `super.create` 或 `context.proceed`。平台按模型与动作检测循环调用，超过 32 层也会拒绝。`create → list` 等同模型不同动作的业务检查可以正常使用。

新增、更新、删除、批量新增/删除、数值调整及状态转移的 Java 逻辑在写事务内运行。通用保存前后抛出异常会回滚该事务中的数据库写入；外部接口等非数据库操作不由本地事务自动撤销。默认批量操作每条记录都经过 `create` 或 `delete` 重写，整批 1～200 条，任何一条失败整批回滚。需要统一规则时优先重写单条动作，让默认批量动作复用；重写批量动作时由该实现维护相同契约。

HTTP 请求仍先校验应用权限。`context.call` 与 JSON 服务步骤一样是可信后端内部调用，沿用调用方行级范围，不发起新的 HTTP 权限检查；处理类负责限定业务允许调用的模型与动作。使用通用实现时保留字段白名单、数据范围、版本检查、只追加和逻辑删除约束；直接使用 JDBC 的定制代码应自行执行相应约束并保持原接口返回结构。处理类是 Spring 单例，不在成员字段中保存请求参数、当前用户或处理结果，不跨线程保存本次上下文。通过上下文调用模型动作，避免注入 MetaEngine 或 CrudExecutor 造成构造依赖循环。

非法模型编码、同一模型重复注册处理类及不存在的模型绑定均拒绝生效。删除或改名一个已绑定模型前，需同步调整 Java 处理类并重新编译启动。JSON 服务继续使用 `service.<编码>` 调用，服务名称相同不会自动覆盖模型 CRUD。

### 3.3 后端批量数据接口

批量新增、删除针对同一模型中的多条业务记录。`params.records` 为1～200个对象的数组；全部记录在同一事务中执行，任一记录失败整批回滚。默认批量动作逐条经过该模型的 Java `create` 或 `delete` 处理方法，继续执行通用校验、版本和数据范围规则。

以下新增两条学生记录，验收时使用未占用的学号：

```json
{"jsonrpc":"2.0","id":1,"method":"student.batchCreate","params":{"records":[{"studentNo":"AC-BATCH-001","name":" 张三 "},{"studentNo":"AC-BATCH-002","name":" 李四 "}]}}
```

成功结果的 `records` 数组包含新增记录及其 `id`、`version`，学生姓名由已注册处理类去除两端空白。删除时将下面的编号和版本替换为该批记录的实际当前值：

```json
{"jsonrpc":"2.0","id":2,"method":"student.batchDelete","params":{"records":[{"id":101,"version":0},{"id":102,"version":0}]}}
```

删除默认使用模型的逻辑删除设置。只追加、服务专用模型以及应用权限、数据范围和版本限制继续适用。接口测试使用有权限的验收账号及有效会话、CSRF令牌。

页面列表按单条记录执行编辑、删除和业务操作，批量数据维护通过后端接口或业务服务调用。通用前端批量操作入口、批量更新和逐条部分成功不属于交付范围。JSONRPC请求数组是多个独立请求的集合，各请求分别执行；其中一个失败不撤销已成功的其他请求。模型批量接口本身不提供请求编号幂等；需要防重时，通过显式配置 `idempotencyKey` 的业务服务调用它。

## 4. 状态、历史、关联和聚合

状态机定义位于模型顶层 `stateMachine`。新记录使用 initial；状态只能通过 `<model>.transition` 更改。状态机 guard 支持简单字段与字面量比较，不执行脚本。调用 `meta.getEvents({model,id})` 查询最近 200 条状态事件。

关联反查示例：

```json
{"jsonrpc":"2.0","id":1,"method":"part_batch.related","params":{"id":1,"model":"assembly_record","field":"batchId","page":1,"pageSize":20}}
```

质量分账汇总示例：

```json
{"jsonrpc":"2.0","id":2,"method":"part_batch.aggregate","params":{"groupBy":["qualityStatus"],"metrics":[{"op":"sum","field":"quantity","as":"quantity"},{"op":"count","as":"batches"}]}}
```

关联还可通过 `paths` 声明多步 ref 跳转，每次最多4条备选路径、每条最多4步。`in` 表示下一模型的字段引用当前模型，`out` 表示当前模型的字段引用下一模型。每一步只接受已声明的 ref 字段，可加该步目标模型的 searchable 字段过滤条件；请求顶层 `filters` 用于最终目标模型。多条路径使用并集，目标记录去重后统计与分页。示例：

```json
{
  "jsonrpc":"2.0","id":3,"method":"part_batch.related",
  "params":{
    "id":1,"model":"assembly_record","page":1,"pageSize":20,
    "paths":[[
      {"model":"assembly_component","field":"batchId","direction":"in","filters":[{"field":"active","op":"eq","value":true}]},
      {"model":"assembly_record","field":"assemblyId","direction":"out"}
    ]]
  }
}
```

模型顶层 `relations` 可保存 `{code,name,target,paths}` 命名关联，详情页自动展示。权限同时检查源、目标和每个中间模型，业务人员不能借关联查询绕过模型读取权限。当前未实现复杂级联写入。聚合结果最多返回1000组，空集合的 SUM 返回0。批量新增、删除的接口及事务约定见3.3节。

引用字段可通过目标 `model.displayTemplate` 定义展示文字，例如 `"{batchNo} · {partName}"`；模板只替换字段值，不执行脚本。服务参数中的 ref 字段可配置 `refFilters` 数组缩小下拉选项，业务守卫仍需在服务端校验。

## 5. 旧数据增量回填

`meta/backfills/*.json` 在应用启动完成示例初始化后执行，配置包括 `code/source/target/keyFields/fields`。字段映射只支持 `{"source":"字段"}` 或 `{"const":标量}`，不接受 SQL。目标须使用 auto 主键，键字段需要非空值。全部配置先校验，再在同一事务中插入缺少的关联；已有匹配键即跳过，包含已停用的历史记录。

当前 `001-assembly-components.json` 将旧整机的主要批次补齐为一条 PRIMARY 位置关联，数量默认为1，不修改原整机或库存。重启可重复执行，热重载不执行回填。该机制用于受控的增量数据补齐，不替代类型变更、约束变更等数据库迁移工具；操作前仍需停机备份。

## 6. BOM版本、齐套和初装核销

生产示例增加三个模型：

| 模型 | 用途 |
| --- | --- |
| `product_bom` | 产品BOM版本头，含全局唯一编码、产品名称、revision版本标签和草稿/发布状态 |
| `bom_item` | 版本的零件位置、零件名称和单机用量 |
| `material_consumption` | 只追加的初装核销记录，关联工单、批次、整机、位置及数量 |

在“BOM与用料”先创建版本，再为草稿增删明细，确认后发布。位置代码须符合 `[A-Z][A-Z0-9_-]{0,49}`，例如 PRIMARY、DIMM_A、SSD-1。一个版本最多100项，发布时至少1项，必须包含且仅包含一个 PRIMARY，主要位置用量必须为1。明细增删与发布均使用版本控制，避免并发修改草稿后发布旧内容。

`createBom`、`addBomItem`、`removeBomItem`、`publishBom` 为公开管理服务；写入均使用请求编号幂等和事务。已发布版本不能通过这些服务再增删明细，变更时创建新的BOM编码，revision仅是标签。模型标记serviceOnly，普通业务人员不能直接CRUD；管理员的data:maintain仍可用于人工修复，所以这里的版本冻结属于业务服务约束，不是数据库级不可变。

`createBomWorkOrder` 接受已发布的bomId、工单编号、计划数量和备注，产品名称来自BOM，计划数量限定1至200。工单保存该版本引用，不跟随新建版本变化。绑定BOM的工单初次登记整机和追加零件时，服务验证位置、零件名称、单机用量，并按下式核销：

```text
同工单同批次的累计初装核销量 + 累计RETURN_UNUSED退库量 + 本次数量
    <= 同工单同批次的累计ISSUE生产领料量
```

库存只在领料时扣减；首次装机建立核销记录，不重复扣仓库可用量。工单版本更新、装配关联和核销写入位于同一事务，并发争用或后续校验失败会一起回滚。返工更换保留原独立库存流程，补领记REWORK_ISSUE，不占用或重复记入初装核销。核销流水记录首次用料，当前在用批次仍应通过装机零件明细和更换履历查询。

`checkBomKit({workOrderId})` 检查装配台数等于计划数量，并逐台核对当前在用位置、零件种类和用量，要求整机状态为RELEASED。推进到TESTING或COMPLETED时自动执行同样检查，缺件、额外位置、数量不符或冻结整机会使整个推进事务失败。当前检查最多200台、每台最多100个位置。

新增work_order.bomId为可空引用。已有无BOM工单和“创建普通工单”入口保留原业务逻辑，升级不会替它们选择版本，也不会依据旧装配记录伪造历史核销。单层BOM不包含多层展开、替代料或工程变更审批；BOM工单的未用料退库见下文。

## 7. 记录附件

在模型的 `model` 对象中配置 `"attachments":true`，重载后该模型记录详情页会增加“附件”页签。当前不良处置 `defect_record` 和质量检验 `quality_inspection` 已启用；其他模型可按同样方式启用。附件不占用业务模型字段，原有凭证链接字段仍可使用。

先保存业务记录，再进入详情页上传。接口为：

| 接口 | 用途 |
| --- | --- |
| `GET /api/attachments?model=模型编码&recordId=主键` | 列出当前记录活动附件 |
| `POST /api/attachments?model=模型编码&recordId=主键` | multipart 表单字段 `file` 上传附件 |
| `GET /api/attachments/{id}/download` | 下载附件 |
| `DELETE /api/attachments/{id}` | 软删除附件 |

所有接口均需登录，写请求携带 CSRF 令牌。读取要求所属模型的读取权限；上传要求读取权限，并具有 `data:write`、`模型编码:write` 或 `data:maintain` 之一；删除还要求当前用户为上传者或具有 `data:maintain`。源记录已软删除、附件已移除、模型未启用附件或当前用户没有读取权限时，不能下载文件。

支持 PNG、JPG、JPEG、WEBP、PDF、TXT、CSV、DOCX、XLSX 扩展名，单文件上限10 MiB，每条记录最多20个活动附件。文件采用随机UUID存储名称，记录SHA-256、上传者、时间和原文件名称；下载统一使用 `application/octet-stream` 和 attachment 响应，不在页面内执行或预览文件。当前仅检查扩展名和大小，不鉴定内容，不提供病毒扫描。

默认目录是项目 `uploads/`，可用 `ATTACHMENT_DIR` 修改；元数据和上传/删除审计分别存于 `t_attachment_file`、`t_attachment_event`，这些表名对元模型保留。软删除保留物理文件与审计；普通上传失败会尽力清理新文件，异常退出仍可能留下孤儿文件。附件数量限制采用单实例同步锁，尚无多实例分布式锁、总存储配额、对象存储和自动保留期清理。

停机备份需同时保存数据库、`meta/` 和 `uploads/` 或配置的实际附件目录。MySQL备份同样需要配套复制附件目录，恢复时数据库记录和文件须来自同一备份批次。

## 8. 余料退库与服务结果展示

在“生产工单”列表的行操作中选择“领料余额”，指定批次后点击“查询余额”；查询结果显示工单、批次、零件名称与四个数量。业务人员选择“余料退库”填写原批次、退库数量和原因，退库记录可在“库存流水”中按工单、批次或“未用料退库”类型筛选。

```text
可退数量 = 同工单同批次ISSUE领料总数
         − material_consumption首次装机核销总数
         − RETURN_UNUSED余料退库总数
```

仅绑定BOM的工单具有完整核销数据，因此旧普通工单不支持此项核算及退库。未冻结的BOM工单在待生产、装配、待检验或完成后均可退回剩余材料；批次须为GOOD且没有未结质量异常。只退回原批次，数量须为正整数且不超过余额，原因必填。退库对库存、工单版本、只追加流水和幂等回执做同一事务更新；并发冲突时整个事务回滚，重新打开表单或按原请求重试。

返工REWORK_ISSUE与RETURN_BAD独立核算，不增加初装可退额度；换下旧件保留首次核销，不会因停用装机关系而变成未用料。装机校验同步扣除RETURN_UNUSED，材料退回后必须重新ISSUE才能再装机。管理员直接维护库存/流水/核销可能影响余额，需配套人工对账。

查询服务 `materialBalance({workOrderId,batchId})` 返回 `orderNo/batchNo/partName/issuedQty/consumedQty/returnedQty/availableQty`；已获生产工单应用查看权限的账号可在可见工单内查询，退库需该应用的业务操作授权。普通业务账号不能直接创建或修改库存流水以绕过服务。

服务表单支持以下可选展示配置；它们只影响呈现，业务校验和权限仍由后端执行：

```json
{
  "description": "按工单与批次查询余料，退库提交时重新校验",
  "submitLabel": "查询余额",
  "resultFields": [{"field": "availableQty", "label": "当前可退数量"}],
  "return": {"availableQty": "guards[0].result.availableQty"}
}
```

`resultFields` 需为1至20个唯一字段，每项必须引用 `return` 对象中的顶层字段，标签为1至80字；`submitLabel` 为1至40字。表单有结果字段时展示结果并保留，修改参数或再次提交会清除旧结果；没有结果字段时成功后沿用原先关闭表单、刷新列表的行为。

## 9. 行级数据范围

管理员在“用户与角色 → 角色与权限 → 编辑角色”中选择“本人及所属记录”或“全部数据”。全部范围对应 `data:scopeAll`；该权限不替代模型读取、写入或业务服务调用权限。多角色按权限并集合并，`data:*` 和管理员的 `*` 也包含全部数据范围。角色权限在每次请求实时解析，调整范围无需用户退出重登。

模型可在 `model` 中声明下列一种规则：

```json
{"rowScope": {"creator": true}}
```

此规则匹配服务端审计字段 `created_by` 与当前登录账号。创建人由服务端记录，客户端不能通过创建、修改或过滤参数伪造。创建人索引在同步结构时自动添加，历史创建人不变更。

```json
{"rowScope": {"via": "workOrderId"}}
```

`via` 必须为真实ref字段，目标模型须已声明数据范围；沿父记录继续继承，最多8跳，循环、未知键及非法目标会使重载失败，保留旧快照。父记录已删除或不可见时子记录也不可见。可用 `allowUnassigned:true` 将空引用的记录明确作为共享数据；非空引用仍需父记录可见。

当前配置：

| 模型 | 数据范围 |
| --- | --- |
| student、equipment、work_order | 当前账号创建 |
| assembly_record、material_consumption | 经workOrderId继承工单 |
| assembly_component、component_change | 经assemblyId继承整机及工单 |
| stock_movement | 经workOrderId继承工单；无工单的批次质量流水共享 |
| 其他现有模型 | 未配置rowScope，仍按功能权限共享 |

列表、总数、聚合、详情、引用校验、更新/删除/adjust/transition、批量操作、关联查询每个跳转、状态历史及附件源记录读取均执行同一规则。客户端过滤与排序不能扩大范围；读取不可见记录与不存在记录均返回“记录不存在”，源记录不可见时附件返回404。关联结果按可见记录去重和分页，共享目的模型不能通过不可见中间记录绕过范围。

批次库存与质量记录为跨工单共享资料，批次发生质量问题时仍需冻结全部受影响整机。内部 `freezeAffected/releaseAffected` 及批次装机计数服务配置 `systemScope:true`，只能由其他服务嵌套调用，须声明 `internalOnly:true` 和显式 `return` 对象。它们临时跨越行范围但保留真实操作人，完成或异常后恢复调用方范围；返回处理标志或计数，不返回其他用户工单明细。外部HTTP和顶层调用均不能直接进入这些服务。普通业务服务保持调用方范围。

幂等服务重放前重新检查其声明的ref参数，摘要还包含当前有效权限及所有模型行范围。权限或范围变化后的旧回执拒绝重放，即使自定义服务没有ref参数也不会沿用旧权限缓存。升级前的回执可能不匹配新的权限摘要；应先核对业务执行记录，再重新打开表单，不能将冲突直接当作业务未执行。

此阶段支持个人创建归属，不提供部门组织、负责人转交、多人协作共享或租户隔离。历史system/admin记录保持原归属，默认仅管理员或授权全部范围的账号可访问；本轮不将历史记录自动转给任何业务账号。管理员可配置只读角色的全部范围，供统一查看工单使用。

## 10. 用户可访问应用

1. 管理员进入“用户与角色 → 角色与权限”，新增角色，例如编码`student_reader`，名称“学生只读”。
2. “按应用授权”树中只勾选“教学示例 → 学生管理”。只勾应用为只读；需要维护学生时再勾“新增/编辑/删除”。勾选父分组会选择其当前子应用，新加入的应用不会自动授权。
3. 工单、BOM和库存等服务专用模型不能直接维护；按需勾“业务操作/附件”，授予该应用视图上声明的公共业务操作及记录附件管理。工单内领料余额等声明data:read的查询服务随应用查看权限开放，无需授予修改操作。仅有附件的应用也可单独勾业务操作/附件。服务内部助手不向用户开放。
4. 选择平台管理权限及记录数据范围后保存，在“用户账号 → 编辑/新增用户”中分配该角色。用户只继承所选角色的应用授权；若只想约束一个人，可以为他建立专用角色。页面不再提供补充权限，API也不接受直接模型、服务或全局业务授权。
5. 用户退出后重新登录，或已登录用户刷新页面。核对菜单、只读按钮和直接接口拒绝；改变角色后无需等待会话过期，后端每次请求都会重新校验。

用户编辑框显示合并后的可访问应用，多角色取并集。“全部数据”只改变应用内部的记录范围，不增加应用入口。默认operator、viewer、modeler角色在初始化或旧权限迁移后会勾选当前全部应用；需要限制时编辑这些角色的应用勾选，或改分配专用角色。

角色编辑只保留应用勾选、平台管理权限和数据范围。业务权限完全由应用勾选决定，取消应用后不能通过旧模型或全局权限继续访问其视图或操作。管理员角色不可编辑；账号名admin或拥有admin角色的账号均禁止资料、角色和启停编辑，禁止管理重置密码，后端同步拦截。管理员本人仍能通过“修改密码”改密，新建管理员必须启用。

应用目录由当前`meta/menus/main.json`的叶子菜单及其视图自动生成。编辑支持普通表单与模型操作；业务操作来自视图按钮所指的公共服务。当前模型ref字段及已授权服务的ref参数所需模型只读开放，供搜索及下拉框使用；这些读取权限也可用于其列表接口，但不会增加对应应用的菜单或视图，不能修改参考数据，记录范围仍然生效。若不应共享某种参考数据，应配置其rowScope或拆分服务，不应只隐藏菜单。反查详情只显示当前已授权读取的模型，完整跨应用追溯需另行授权相关应用。

技术上，授权保存在角色表permissions_json，允许app_菜单编码:view/edit/operate、data:scopeAll及三个平台管理权限。非管理员身份逐次过滤其他旧权限，模型读取、写入、视图、服务和附件鉴权只从应用配置推导，不能利用旧通配符绕过。服务端继续拒绝不存在的应用、无查看权限的应用操作授权及不支持的动作。内部服务拒绝顶层调用，服务专用模型仅管理员可直接维护。元模型重载后应用目录同步变化；旧菜单删除或能力关闭后，角色编辑器提示移除失效授权。

启动时在事务内迁移旧角色，迁移前完整保存角色名称、原权限及时间到t_sys_role_permission_backup表，重复启动不会为相同配置重复迁移。已有app_勾选或旧apps:configured标记的角色，以显式应用和平台/范围选项为准，移除其他旧权限。只有旧模型/全局授权的角色按旧可读模型转换到应用：普通维护随原写权限转换，业务操作只有原权限已覆盖该应用全部公共服务时才启用，避免从单个服务扩大到全部操作；无法等价映射的自定义或部分服务权限不继续生效，管理员可重新勾选。管理员admin角色不迁移。旧账号和密码不修改。

用户与角色管理权限允许重新分配授权，应仅授予可信管理员。它不受应用选择限制。

删除自定义角色时，在“角色与权限”列表操作列选择“删除”并确认。系统保留admin、modeler、operator、viewer内置角色；自定义角色只要仍分配给未删除用户就禁止删除，停用用户同样计入，已逻辑删除用户不再占用。先在用户编辑里改用其他角色并保存，再返回删除；按钮提示分配人数，后端会重新核对，避免页面数据过期造成误删。取消确认不会发送删除请求。

接口为DELETE /api/auth/roles/{code}，需要users:manage及有效CSRF令牌。内置角色返回403，仍被分配返回409，不存在返回404；成功后从角色列表移除并备份原权限、记录roles.delete.角色编码审计。分配角色和删除角色通过事务锁串行化，避免刚删除的角色又被分配。删除操作不删除用户、迁移备份或业务记录，暂无界面恢复入口。

### 用户逻辑删除

在“用户账号”列表操作列选择“删除”并确认，账号随即从正常列表隐藏，无法再次登录，全部旧会话撤销。停用仅用于暂时限制登录，账号仍显示且可重新启用；逻辑删除用于退出使用，当前没有回收站、恢复或永久清除入口。

账号名admin、拥有admin角色的用户以及当前登录用户不可删除。删除需要users:manage和有效CSRF令牌，前端禁用受保护按钮，后端独立检查。接口为DELETE /api/auth/users/{id}?version={当前版本}：缺少或无效参数400，无权限/管理员目标403，账号不存在或已删除404，版本过期409。当前登录用户作为目标返回400。版本变化时刷新列表后重新确认。

t_sys_user新增deleted、deleted_at、deleted_by，启动时自动为旧表追加，已有用户默认为未删除，已有密码和角色不修改。删除在同一事务内锁定账号、校验版本、标记删除并停用、递增版本、清除会话和写入users.delete.用户ID审计。登录创建会话前再次锁定并检查账号，避免与删除并发产生可用会话。已删除用户的编辑、重置密码及重新登录均拒绝，用户名保留唯一约束，不能重新注册同名账号。

用户ID、姓名、原角色及密码哈希仍保存在数据库；学生、工单、BOM、附件和历史审计不随账号删除，创建归属保持原账号。管理员或具有相应全部数据范围的账号可继续按原有权限查看历史业务。已删除用户原角色仅作历史保存，不阻止角色删除；若今后增加恢复功能，必须重新校验角色和授权，不能直接恢复旧权限。

## 11. 图表与整机直通率

管理员可从“生产装配 → 整机检验与直通率”进入，点击“登记整机检验”，选择整机并填写结果、工时和说明。角色需要该应用的访问与业务操作授权；应用按整机所属工单继承数据范围。

直通率=首次检验通过台数÷首次受检台数。每台整机按记录编号取第一条有效检验，之后复检不改变首次结果；未登记检验的整机不参与分母。例如三台中两台首次通过、另一台首次失败后复检通过，直通率为 66.67%，检验记录共有四条。该登记记录检验事实，冻结和放行仍走不良处置服务。

视图的 `chart` 数组支持 `bar`、`line`，配置 `groupBy`、`metrics`、`ratios` 和 `series`；`firstBy:"assemblyId"` 表示每台整机选首次记录后统计。图表跟随已提交的页面筛选，先确定首次记录再应用筛选。质量检验应用还提供供应商不良率及检验/返工工时图表，数量合格率与整机直通率分别展示。

## 12. 服务调用日志

具有 `users:manage` 权限的用户进入“平台管理 → 服务调用日志”。可按服务编码、操作人、执行结果、根调用编号及幂等键精确筛选，并查看详情或同一调用链。

执行结果包括成功、失败、随事务回滚和幂等结果重放。嵌套调用保留上级及根调用编号；共享事务保留相同平台逻辑事务编号。业务回滚后日志仍保留。日志只保存参数名称及 SHA-256 摘要，不保存原始参数值。

## 13. 生产化边界

当前已实现登录、基础角色权限、服务端鉴权和真实操作人审计；元模型由引擎执行结构和语义校验。多租户、复杂级联、通用报表与后台消息任务属于交付范围外的生产化能力。实际验证记录见[交付与验收记录](05-迭代交付与验收记录.md)，正式交付前的执行事项见[收尾任务清单](08-收尾任务清单.md)。
