## 1. 引言

### 1.1 编写目的

从技术、经济、操作、法律、进度等维度论证"模型驱动开发低代码平台"项目实施的可行性，为项目立项决策提供依据。

### 1.2 项目背景

本项目旨在构建一个基于元数据驱动的低代码平台：业务模型通过 JSON 元模型文件定义，后端元模型引擎解析后动态生成 JSONRPC 服务接口（每个模型自动具备增删改查能力），菜单与视图（表格、搜索区、表单）同样以元模型描述，前端引擎根据后端下发的元数据动态渲染页面，视图按钮可直接调用模型服务。详细需求见《需求分析文档》。

### 1.3 可行性研究的前提

**（1）基本要求**

- 后端基于 Java 技术栈，业务模型与服务接口使用 JSONRPC 2.0，账号会话和附件使用受会话保护的 REST 接口；
- 新增一个业务模型，从编写 JSON 到页面可用的全过程不修改 Java/前端代码；
- 支持元模型热更新，更新失败不影响线上服务。

**（2）目标**

- 近期目标：按《需求分析文档》第 9 章验收标准（AC-01 ~ AC-23）完成首版平台；
- 长期目标：形成可复用的业务建模资产库，沉淀为团队标准开发底座。

**（3）假定与限制**

- 建模人员具备 JSON 编写能力；
- 单体部署可满足本期并发要求，不考虑多租户与分布式；
- 本期不提供可视化建模界面，建模通过编辑 JSON 文件完成。
- 批量能力以同一模型的后端批量新增、删除为范围，每批 1～200 条，整批成功或回滚；前端通用批量入口、批量更新、部分成功返回及专用扫码采集页面不纳入交付。

**（4）评价尺度**

- 验收标准 AC-01 ~ AC-23 全部通过；
- 新模型零代码上线全流程 ≤ 30 分钟；
- 元模型热更新耗时 ≤ 5 秒，且更新期间服务不中断；
- list 服务 P95 响应 ≤ 1s（单表百万级数据）。

## 2. 技术可行性分析

### 2.1 技术路线与选型成熟度

| 技术领域 | 选型 | 成熟度评估 |
| -------- | ---- | ---------- |
| 开发语言/框架 | Java 17 + Spring Boot 3.x | 行业主流，生态完善，团队储备充足 |
| RPC 协议 | JSONRPC 2.0 | 协议极简（单端点 + method 分发），无强绑定框架，实现成本低 |
| 元模型校验 | Jackson JsonNode + MetaEngine 结构与语义校验 | 以 JSON 节点遍历校验必填项、类型、枚举及跨定义引用，统一返回文件和路径错误明细 |
| 数据访问 | Spring JDBC（JdbcTemplate）+ 动态 SQL 拼装 | 相比 ORM 更贴合"元数据 → SQL"的动态生成场景，可控性强 |
| 数据库 | H2（本地文件库及内存测试）/ MySQL（测试与部署可选） | 当前适配与验收覆盖这两种数据库，按 JDBC 元数据识别数据库并处理 DDL 差异 |
| 前端框架 | Vue 3 + Element Plus + Vite | 动态组件渲染（`<component :is>`）能力原生支持"配置驱动页面" |
| 热更新 | 目录扫描 + 原子快照替换 | 纯应用层实现，不依赖字节码增强或类加载器黑魔法，风险低 |

**结论**：全部选型均为成熟、主流、开源的技术，无实验性技术引入，技术路线可行。

平台功能覆盖账号会话、应用授权、继承式数据范围、记录附件、单层 BOM、装机核销、余料退库、质量图表、整机直通率与可追溯服务日志。采用同源访问方案：开发时通过 Vite 代理，部署时由后端托管静态资源或由反向代理统一转发接口。

JSONRPC 数组按独立请求处理，不提供数组级整体事务。同一模型的 `batchCreate`、`batchDelete` 在后端使用整批事务，并复用单条 Java 处理类规则。重复提交去重由显式声明幂等键的事务服务提供，普通 CRUD 与模型批量接口不自动具备幂等能力。

### 2.2 关键技术难点分析与论证

| 编号 | 难点 | 分析与论证 | 结论 |
| ---- | ---- | ---------- | ---- |
| T1 | 元模型解析与多重校验 | Jackson 将 JSON 解析为 JsonNode；MetaEngine 按节点检查必填项、类型、枚举及字段约束，并检查模型编码唯一、视图引用模型、菜单引用视图、服务调用目标等语义规则；错误按文件与路径统一收集，校验流程明确 | 低风险 |
| T2 | 动态 JSONRPC 服务生成与模型扩展 | 采用统一入口与 method 路由分发。`RpcDispatcher` 按 `<modelCode>.<action>` 解析方法，`CrudExecutor` 在事务边界内选择该模型的 Java 处理类或通用实现；新增普通模型不需要生成 Java 类，复杂业务可重写指定动作并继续调用通用逻辑 | 低风险 |
| T3 | 动态 SQL 与自动建表 | SQL 由元模型白名单字段拼装 + 全参数化（`BoundSql: sql + args`）；DDL 同步限定为"建表 + 追加列"两种安全操作，破坏性变更仅告警。字段类型→SQL 类型映射表固定且可穷举 | 中低风险（需专项测试防注入） |
| T4 | 元模型热更新 | 采用**不可变快照（MetaSnapshot）+ volatile 原子替换**：重载期间旧快照继续服务，新快照校验通过后一次性切换；校验失败保持旧快照。无锁竞争，实现简洁且一致性好 | 低风险 |
| T5 | 前端动态渲染 | 表格/表单本质是"JSON 配置 → 组件树"映射，业界已有成熟先例（百度 amis、form-create、JeecgBoot 在线表单均为此模式）；本期控件类型可穷举（input/number/select/date/switch 等约 10 种），映射矩阵封闭可控 | 中低风险（控件联动场景需控制范围） |
| T6 | 按钮动作与服务调用 | 动作协议为简单字符串语法（`openForm:xxx` / `service:model.action`），前端动作调度器为有限状态逻辑（解析→确认→组装参数→调用→后置行为），无复杂编排 | 低风险 |

### 2.3 同类产品与先例验证

| 产品/项目 | 模式 | 对本项目的佐证 |
| --------- | ---- | -------------- |
| 百度 amis | JSON 配置生成页面，组件百余种 | 证明"JSON 驱动前端渲染"在大规模生产环境可行 |
| JeecgBoot / 若依 | 在线表单 + 代码生成 | 证明"模型定义自动产出接口与页面"是成熟工程实践 |
| Spring Data JDBC 元数据驱动 | 无实体类的动态数据访问 | 证明"无预定义实体"的动态 CRUD 在 Java 生态可行 |

本项目相对上述产品的差异化（JSONRPC 协议、更轻量的元模型范围）均属**做减法**，复杂度不高于先例。

### 2.4 技术风险与规避措施

| 风险 | 等级 | 规避措施 |
| ---- | ---- | -------- |
| 动态 SQL 拼装引入注入漏洞 | 高 | 字段名/操作符/排序字段仅从元模型白名单匹配；值全参数化；专项安全测试用例覆盖非法字段、非法操作符、恶意值 |
| 表结构自动变更误操作 | 中 | 仅允许 CREATE TABLE / ADD COLUMN；变更前 diff 输出日志；破坏性变更仅告警人工处理 |
| 热更新期间请求读到不一致元数据 | 中 | 快照整体原子替换（不可变对象），单次请求全程持有同一快照引用 |
| 前端控件与元数据组合不支持 | 中 | 控件映射矩阵封闭（类型×控件）；元模型校验阶段拦截不支持组合 |
| 校验规则遗漏导致脏数据 | 中 | 应用层校验 + 数据库层约束（NOT NULL / UNIQUE INDEX）双重兜底 |

### 2.5 技术可行性结论

**可行。** 所有技术选型成熟主流，6 项关键技术难点中无高风险项，且均有明确、经过业界验证的实现路径；团队（中级开发人员）具备全部所需技术储备。

## 3. 经济可行性分析（成本分析）

### 3.1 估算方法与基本假设

- **方法**：自下而上工作量分解（WBS）+ 专家判断法；估算结果给出乐观/中性/悲观三档；
- **人力单价假设**：中级工程师综合成本（工资 + 五险一金 + 工位设备摊销）按 **2.2 万元/人月** 计；
- **估算口径**：一次性开发投入 + 年度运行成本 vs 年度节约收益，静态回收期与三年期 ROI。

### 3.2 开发成本估算

**（1）工作量分解（WBS）**

| 工作项 | 工作量（人月） | 说明 |
| ------ | -------------- | ---- |
| 需求分析与设计 | 1.5 | 需求分析、概要/详细设计、评审（已完成部分不计入） |
| 元模型引擎 | 1.5 | 文件加载、结构/语义校验、快照仓库、热更新 |
| JSONRPC 网关与动态服务 | 1.5 | 统一入口、method 路由分发、错误码体系、登录鉴权 |
| 动态 CRUD 与数据访问层 | 1.5 | QueryBuilder、SqlBuilder、DdlSynchronizer、方言适配、ID 生成 |
| 元数据服务 | 0.5 | meta.getMenus / getViews / getModel / reload / status |
| 前端引擎 | 2.5 | 菜单渲染、列表视图、表单视图、控件库、动作调度器 |
| 测试 | 1.5 | 单元测试、集成测试、安全专项测试、按 AC-01~AC-23 验收测试 |
| 部署与文档 | 0.5 | 部署脚本、用户手册（建模指南） |
| **合计** | **11.0 人月** | |

**（2）成本构成**

| 成本项 | 金额（万元） | 说明 |
| ------ | ------------ | ---- |
| 人力成本 | 11 × 2.2 = **24.2** | 开发 + 测试 + 设计全过程人力 |
| 硬件/环境 | **3.0** | 开发机、测试服务器（一次性，按 3 年摊销实际计入约 1.0/年） |
| 云资源 | 0.6 / 年 | 应用服务器 + 数据库云主机（1 台 4C8G 即可满足单体部署） |
| 软件许可预算 | 0 | 基于当前实训交付方式估算，依赖及使用方式说明见第 5 章 |
| 风险预备金 | 约 2.7（10%） | 应对估算偏差 |
| **一次性总投入** | **约 30 万元** | 含预备金 |
| **年度运行成本** | **约 2 万元/年** | 云资源 0.6 + 兼职运维人力约 0.6 人月 1.4 |

### 3.3 收益分析

**（1）单模块开发效率对比**

以一个典型业务模块（如"学生管理"：1 张表、5~8 个字段、列表页 + 表单页、标准 CRUD）为基准：

| 开发活动 | 传统开发（人天） | 平台模式（人天） | 说明 |
| -------- | ---------------- | ---------------- | ---- |
| 建表 / 实体 / DAO / Mapper | 3 | 0 | 元模型注册后自动完成 |
| CRUD 接口开发与自测 | 3 | 0 | 动态生成 |
| 列表页 / 表单页开发 | 5 | 0.5 | 仅编写视图 JSON |
| 菜单与联调 | 1 | 0.5 | 菜单 JSON + 前后端联调 |
| 测试 | 3 | 2 | 校验规则自动生效，测试量下降 |
| **合计** | **15** | **3** | **节约 12 人天/模块（80%）** |

**（2）年度节约测算（中性情景）**

- 假设平台上线后年均支撑 **12 个**业务模块的开发/迭代；
- 年节约 = 12 模块 × 12 人天 = **144 人天 ≈ 6.9 人月 ≈ 15.2 万元/年**；
- 未计入的隐性收益：代码质量一致性提升、模板代码缺陷减少、新业务响应速度加快、建模 JSON 资产可复用与版本化管理。

### 3.4 投资回收与敏感性分析

| 情景 | 年均支撑模块数 | 年节约（万元） | 净年收益（扣除运行成本 2 万） | 静态回收期 | 三年期 ROI |
| ---- | -------------- | -------------- | ---------------------------- | ---------- | ---------- |
| 悲观 | 6 | 7.6 | 5.6 | ≈ 5.4 年 | -44%（含隐性收益后约打平） |
| 中性 | 12 | 15.2 | 13.2 | ≈ 2.3 年 | **+32%** |
| 乐观 | 20 | 25.3 | 23.3 | ≈ 1.3 年 | **+133%** |

**敏感性说明**：回收期对"年均支撑模块数"最敏感。若平台作为团队级底座同时服务 2 个以上项目（模块数相应叠加），即可达到中性及以上情景；若仅为单个小项目服务（悲观情景），则经济性不成立，此时应评估其作为**实训/能力建设投入**的价值而非纯 ROI。

### 3.5 经济可行性结论

**可行（有条件）。** 中性情景下约 2.3 年收回投入，三年期 ROI 约 +32%；只要平台被作为通用底座支撑多个业务模块/项目，经济性成立。

## 4. 操作可行性分析

### 4.1 各角色操作分析

| 角色 | 操作方式 | 学习成本 | 接受度评估 |
| ---- | -------- | -------- | ---------- |
| 建模人员 | 编辑 JSON 文件（模型/视图/菜单）→ 调用重载 | 低：JSON 语法 + 一份《建模指南》即可上手；元模型结构简单、有大量示例；校验错误信息指明文件与原因 | 高：对比写全栈代码，工作量下降约 80% |
| 业务用户 | 标准网页操作：菜单导航、表格查询/分页、表单录入 | 极低：均为常规增删改查页面，无新交互范式 | 高：无感知切换 |
| 平台管理员 | 调用重载接口、查看加载状态与错误清单 | 低 | 高 |

### 4.2 组织影响评估

- 不改变现有开发流程与组织架构，仅将"模板化编码"环节替换为"声明式建模"；
- JSON 元模型文件纳入 Git 管理，建模变更具备可评审、可回滚能力，与现有研发流程兼容；
- 风险点：建模人员初期对约束声明（unique/min/max 等）不熟悉可能导致校验反复——通过《建模指南》+ 校验错误明细闭环快速缓解。

### 4.3 操作可行性结论

**可行。** 各角色操作成本均低于被替代的传统方式，无组织阻力。

## 5. 法律与社会可行性

### 5.1 开源协议合规

项目数据库支持范围为 H2/MySQL。后端依赖由 `platform-server/pom.xml` 记录，前端依赖由 `platform-web/package.json` 及锁文件记录，第三方组件的许可说明以各依赖附带文件为准。

### 5.2 其他法律事项

- 平台自研源码与第三方依赖通过项目目录和构建配置区分；
- 演示与验收采用专用账号和测试数据，源码、交付材料与录屏不包含真实凭据。

### 5.3 法律可行性结论

本报告记录实际技术依赖与使用方式，不对特定发行方式作法律结论。

### 6.3 进度可行性结论

**可行。** 3 人团队 4 个月完成首版，里程碑与依赖关系明确。
