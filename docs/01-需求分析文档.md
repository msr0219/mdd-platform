## 1. 引言

### 1.1 编写目的

本文档描述"模型驱动开发低代码平台"（以下简称"本平台"）的功能需求与非功能需求，作为后续概要设计、详细设计与编码实现的依据。本文档的预期读者为：系统设计人员、开发人员、测试人员及项目管理人员。

### 1.2 项目背景

传统业务系统开发中，大量时间消耗在重复性的"建表 → 写实体 → 写 DAO → 写 Service → 写接口 → 写列表页/表单页"的模板化工作上。本平台采用**模型驱动开发（Model Driven Development, MDD）**思想：

- 业务模型（实体、属性）通过 **JSON 元模型文件**声明式定义；
- **元模型引擎**解析元模型后，**动态生成 JSONRPC 格式的服务接口**，每个模型自动具备增、删、改、查（CRUD）能力；
- 菜单、视图（表格、搜索区域、表单）同样以元模型描述；
- **前端引擎**根据后端下发的元模型信息**动态渲染菜单与视图**，视图上的按钮可直接绑定并调用模型服务。

由此实现"定义模型即可获得接口与页面"的低代码开发体验，将开发人员从重复劳动中解放出来，聚焦于真正的业务逻辑。

### 1.3 术语与缩略语

| 术语 | 说明 |
| ---- | ---- |
| 元模型（Meta-Model） | 描述"模型如何定义"的规则，即本平台用来定义业务模型的 JSON 结构规范 |
| 模型（Model） | 由元模型定义的一个业务实体，如"学生"、"课程" |
| 属性（Field/Attribute） | 模型中的字段，如"学生姓名"、"入学日期" |
| 视图（View） | 前端页面的元数据描述，本平台主要包含列表视图与表单视图 |
| JSONRPC | 一种基于 JSON 的远程调用协议（本平台采用 JSONRPC 2.0） |
| CRUD | Create / Read / Update / Delete，增删改查 |
| 元数据服务 | 向前端提供菜单、视图等元模型信息的查询服务 |
| 前端引擎 | 根据元数据动态渲染菜单与视图的前端运行时 |
| 自定义服务（Service） | 由 JSON 声明、含参数与事务步骤编排的一等元模型，注册后自动暴露为 `service.*` JSONRPC 方法 |
| 动态路由 | 前端运行时依据菜单树元模型调用 `addRoute` 生成的路由表，而非硬编码的路由配置 |
| 状态机（State Machine） | 模型上声明的状态集合与允许的转移规则，用于表达业务单据的生命周期 |
| 建模人员 | 通过编写/维护 JSON 元模型文件来定义业务模型的角色 |
| 业务用户 | 通过前端页面进行日常业务操作的角色 |

## 2. 项目概述

### 2.1 项目目标

1. 提供一套**基于 JSON 的元模型规范**，支持定义业务模型及其属性；
2. 提供**元模型引擎**，完成元模型的加载、解析、校验与注册，并支持热更新；
3. 基于元模型**动态生成 JSONRPC 2.0 服务接口**，每个模型自动获得标准 CRUD 服务；
4. 支持以元模型方式定义**菜单与视图**（表格、搜索区域、表单）；
5. 提供**元数据服务**，向前端下发菜单树与视图定义；
6. 提供**前端引擎**，根据元数据动态渲染菜单、表格、搜索区、表单，并支持按钮调用模型服务。

### 2.2 系统范围

**本期范围内（In Scope）：**

- 元模型定义规范（模型、属性、菜单、视图）；
- 元模型引擎（解析、校验、注册、热加载）；
- JSONRPC 统一入口与动态服务生成；
- 模型级动态 CRUD 服务（含分页、过滤、排序及后端批量新增、删除接口）；
- **自定义服务元模型**（参数声明、事务步骤编排、幂等键、前置守卫）及其执行编排器；
- 元数据查询服务（菜单树、视图定义、模型定义）；
- 前端引擎（菜单渲染、**由菜单元模型动态生成前端路由**、列表视图、搜索区、表单视图、按钮动作）；
- **生产场景通用支撑能力**（状态机、关联反查、只追加流水、聚合查询、条件可见性、权限、乐观锁）；
- 账号会话、用户与角色、应用授权、数据范围、记录附件；
- 单层 BOM、装机领料核销、余料退库、质量图表、整机直通率及服务调用日志。

**范围外（Out of Scope）：**

- 可视化拖拽建模界面（本期通过编辑 JSON 文件完成建模）；
- 模型间复杂级联写入维护；关联查询使用 ref 和 relations/paths 协议；
- 多租户、部门组织、负责人转交及多人共享数据范围；
- 通用审批工作流及自由布局报表设计器；
- 前端通用批量操作入口、批量更新、批量记录逐条部分成功返回及专用扫码采集页面；
- 移动端适配。

### 2.3 用户角色

| 角色 | 描述 | 主要操作 |
| ---- | ---- | -------- |
| 建模人员 | 懂得业务、熟悉 JSON 的开发/实施人员 | 编写并维护元模型 JSON 文件（模型、菜单、视图），触发重载 |
| 业务用户 | 使用系统完成日常业务操作的人员 | 登录后通过菜单进入视图，进行数据的增删改查、执行按钮动作 |
| 平台管理员 | 维护平台运行的人员 | 监控元模型加载状态、处理校验错误、管理热更新 |

### 2.4 核心设计理念

1. **元数据驱动**：一切业务表达（模型、接口、页面）皆由元数据描述，运行时解释执行；
2. **约定优于配置**：为模型命名、服务命名、通用字段（主键、审计字段）提供默认约定，减少配置量；
3. **前后端契约明确**：业务页面使用元数据查询与 JSONRPC 业务调用，账号、会话和附件使用受会话保护的平台 REST 接口；
4. **渐进式增强**：标准 CRUD 满足通用场景，自定义服务承接业务编排，二者共用同一分发入口；
5. **场景抽象化**：真实业务中的异常流（不良品、返工、追溯、并发、幂等）一律沉淀为元模型的通用能力，不在上层系统硬编码；
6. **路由亦为元数据**：前端导航、页面与路由三者均由同一份菜单/视图元模型派生，避免前端出现第二份需要手工同步的配置。

## 3. 总体架构

### 3.1 架构总览

```
┌────────────────────────────────────────────────────────────┐
│                        前端引擎（浏览器）                    │
│   菜单渲染 │ 列表视图(表格+搜索区) │ 表单视图 │ 按钮动作调度  │
└──────────────┬─────────────────────────────▲───────────────┘
               │ ① 元数据请求                  │ ② JSONRPC 业务请求
               │ (菜单/视图定义)               │   (student.create 等)
               ▼                             │
┌──────────────────────────────────────────────┴─────────────┐
│                     后端应用（Java / Spring Boot）           │
│                                                            │
│  ┌─────────────────┐      ┌─────────────────────────────┐  │
│  │  元数据服务       │      │  JSONRPC 统一网关/分发器      │  │
│  │  meta.getMenus  │      │  method → 模型服务路由        │  │
│  │  meta.getViews  │      └──────────────┬──────────────┘  │
│  └────────┬────────┘                     ▼                 │
│  ┌────────┴──────────────────────────────────────┐         │
│  │  元模型引擎                                    │         │
│  │  加载 → 解析 → 校验 → 注册 → (热更新)           │   ▼     │
│  └────────┬──────────────────────────────────────┘  动态   │
│           ▼                                         服务   │
│  ┌──────────────────┐   ┌──────────────────────────┐  执行  │
│  │ 元模型仓库（内存） │   │ 动态 CRUD 服务层           │  器   │
│  │ Model/Menu/View  │   │ 校验 → 构造查询 → 执行      │       │
│  └──────────────────┘   └────────────┬─────────────┘       │
└───────────┬──────────────────────────┼─────────────────────┘
            │ 启动/重载时读取            ▼
     meta/**/*.json              业务数据库（动态 CRUD）
     (models/views/menus/services)
```

### 3.2 核心模块职责

| 模块 | 职责 |
| ---- | ---- |
| 元模型定义（JSON 文件） | 以声明式 JSON 描述模型、属性、菜单、视图，是平台的唯一业务输入 |
| 元模型引擎 | 扫描并加载 JSON 文件；按元模型规范进行结构与语义校验；校验通过后注册到内存元模型仓库；支持启动加载与运行期热更新 |
| 元模型仓库 | 以内存数据结构持有所有已注册的模型、菜单、视图定义，供元数据服务与服务执行器查询 |
| JSONRPC 网关 | 提供 JSONRPC 2.0 统一入口，按 `modelCode.action` 规则将 method 分发到对应的动态服务；统一错误码处理 |
| 动态服务执行器 | 根据模型定义动态执行 create / read / update / delete / list 等服务；执行参数校验、数据校验 |
| 服务编排器 | 解析自定义服务定义，执行前置守卫、事务步骤编排、幂等去重与失败回滚，并记录调用日志 |
| 数据访问层 | 依据模型定义动态拼装 SQL，完成业务数据的持久化（支持自动建表） |
| 元数据服务 | 面向前端，提供菜单树、视图定义等元数据的查询接口 |
| 前端引擎 | 请求元数据 → 渲染菜单与视图；将按钮动作转换为 JSONRPC 调用；渲染数据与操作反馈 |

### 3.3 关键数据流

1. **建模流程**：建模人员编写 `models/student.json` → 触发重载 → 元模型引擎校验并注册 → 平台自动具备 `student.create / student.read / student.update / student.delete / student.list` 等服务。
2. **页面访问流程**：业务用户打开页面 → 前端引擎调用 `meta.getMenus` 渲染菜单 → 点击菜单项 → 调用 `meta.getViews` 获取视图定义 → 渲染搜索区与表格 → 调用 `student.list` 加载数据。
3. **业务操作流程**：业务用户在表单点击"保存" → 前端按钮动作调度器将动作解析为 `student.create` 的 JSONRPC 请求 → 后端校验并入库 → 返回结果 → 前端刷新表格。

## 4. 功能需求

> 需求编号规则：`FR-<模块>-<序号>`；优先级：高（首版必须）、中（首版应尽量实现）、低（可延后）。

### 4.1 元模型定义（FR-MODEL）

#### 4.1.1 模型定义

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-MODEL-01 | 支持通过 JSON 文件定义模型，每个模型一个文件（目录约定见 6.1），文件内容包含模型基本信息与属性列表 | 高 |
| FR-MODEL-02 | 模型基本信息包括：唯一编码（code，全平台唯一）、显示名称（name）、描述（description）、对应物理表名（table，可缺省并按约定自动生成）、主键策略（自增/雪花/UUID，默认自增） | 高 |
| FR-MODEL-03 | 平台为每个模型自动补充审计字段：created_by、created_at、updated_by、updated_at、deleted（逻辑删除标记），建模人员无需声明 | 高 |
| FR-MODEL-04 | 支持启用/禁用逻辑删除（默认启用：删除操作仅标记 deleted=1） | 中 |
| FR-MODEL-05 | 支持模型级配置：是否启用 list 服务默认分页、默认排序字段 | 低 |

#### 4.1.2 属性定义

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-FIELD-01 | 每个属性可定义：编码（code）、显示名称（name）、数据类型（type）、描述 | 高 |
| FR-FIELD-02 | 支持的基础数据类型：string（可定义 length）、text、integer、decimal（可定义 precision/scale）、boolean、date、datetime、enum（可定义选项列表 value/label） | 高 |
| FR-FIELD-03 | 支持引用类型 ref：引用另一个模型的编码，用于下拉选择等场景（本期以存储被引用模型主键实现） | 中 |
| FR-FIELD-04 | 支持约束定义：required（必填）、unique（唯一）、min/max（数值或字符串长度）、正则（pattern）、默认值（defaultValue） | 高 |
| FR-FIELD-05 | 支持界面行为声明：searchable（是否可搜索）、listable（是否出现在列表）、editable（是否可编辑）、hidden（是否隐藏） | 高 |

### 4.2 元模型引擎（FR-ENGINE）

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-ENGINE-01 | 应用启动时，自动扫描约定目录下全部元模型 JSON 文件（models / views / menus / services）并加载 | 高 |
| FR-ENGINE-02 | 结构校验：通过 Jackson 解析 JSON，由元模型引擎检查必填节点和节点类型 | 高 |
| FR-ENGINE-03 | 语义校验：模型 code 唯一；视图引用的模型必须已定义；菜单引用的视图必须已定义；属性 code 唯一且合法；视图字段必须属于所引用模型 | 高 |
| FR-ENGINE-04 | 校验失败处理：启动期校验失败则应用启动失败并输出明确的错误清单（文件名、错误位置、原因）；热更新期校验失败则保持旧版本元模型继续运行，并记录错误日志与提示 | 高 |
| FR-ENGINE-05 | 元模型注册：校验通过后写入内存元模型仓库，并按需同步数据库结构（见 FR-DB-01） | 高 |
| FR-ENGINE-06 | 热更新：提供管理接口（如 `meta.reload`）触发重新加载，无需重启应用；重载期间服务不中断，成功后新定义立即生效 | 高 |
| FR-ENGINE-07 | 提供元模型查询管理接口：列出已加载的模型/视图/菜单清单及其加载状态 | 中 |

### 4.3 动态 JSONRPC 接口生成（FR-RPC）

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-RPC-01 | 后端对外提供 JSONRPC 2.0 统一入口（单个 HTTP 端点，如 `POST /rpc`），所有模型服务通过该入口调用 | 高 |
| FR-RPC-02 | 请求符合 JSONRPC 2.0 规范，支持命名参数对象及不带 `id` 的通知；数组请求含 1～200 项，每项独立鉴权、执行与返回结果，不提供数组级整体事务 | 高 |
| FR-RPC-03 | 服务命名约定：`<模型编码>.<动作>`，如 `student.create`、`student.list` | 高 |
| FR-RPC-04 | 每个已注册模型自动暴露 create（创建）、read（按 ID 查询）、update（更新）、delete（删除，默认逻辑删除）、list（分页查询）及后端 batchCreate/batchDelete（批量新增、删除）服务 | 高 |
| FR-RPC-05 | 方法不存在时返回 JSONRPC 标准错误 `-32601 Method not found`；参数不合法返回 `-32602 Invalid params`，并在 error.data 中给出具体校验信息 | 高 |
| FR-RPC-06 | 业务错误码在 `-32000 ~ -32099` 区间定义（如校验失败、记录不存在、唯一约束冲突），错误信息可读且稳定 | 高 |
| FR-RPC-07 | 响应统一封装：成功返回 `result`（含业务数据），失败返回 `error`（code/message/data） | 高 |

**JSONRPC 请求/响应示例：**

请求（创建学生）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "student.create",
  "params": { "studentNo": "S2026001", "name": "张三", "gender": "M", "age": 20, "enrollDate": "2026-09-01" }
}

```

成功响应（省略审计字段）：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": { "id": 1001, "version": 0, "studentNo": "S2026001", "name": "张三", "gender": "M", "age": 20, "enrollDate": "2026-09-01" }
}

```

缺少姓名时的失败响应：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32001,
    "message": "数据校验失败",
    "data": { "fields": [{ "code": "name", "message": "姓名不能为空" }] }
  }
}
```

### 4.4 动态 CRUD 服务（FR-CRUD）

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-CRUD-01 | **create**：入参为属性键值对；仅接受模型中 editable 属性；执行约束校验（required/unique/min/max/pattern/枚举值合法性）后入库；返回含主键的完整记录 | 高 |
| FR-CRUD-02 | **read**：入参为主键 id；返回单条记录；记录不存在返回业务错误码 | 高 |
| FR-CRUD-03 | **update**：入参包含主键 id、version 与待更新字段；仅更新 editable 且出现在入参中的字段；校验规则同 create | 高 |
| FR-CRUD-04 | **delete**：入参为主键 id 和 version；默认逻辑删除（deleted=1），逻辑删除关闭的模型物理删除 | 高 |
| FR-CRUD-05 | **list**：支持分页（page/pageSize，默认 1/20）、排序（sortField/order，仅允许 listable 字段）、条件过滤（见 FR-CRUD-06）；返回 `{total, records}` 结构 | 高 |
| FR-CRUD-06 | 条件过滤：支持操作符 eq（等于）、ne、like（模糊）、gt/ge/lt/le（比较）、in、between；过滤字段必须声明为 searchable；非法字段/操作符直接拒绝 | 高 |
| FR-CRUD-07 | 所有查询默认过滤已逻辑删除数据 | 高 |
| FR-CRUD-08 | 数据校验失败时返回字段级错误明细（字段编码 + 错误信息），供前端表单回显 | 高 |
| FR-CRUD-09 | SQL 参数化执行，杜绝 SQL 注入；字段名/操作符仅从元模型白名单匹配 | 高 |
| FR-CRUD-10 | 支持以 Java 处理类绑定指定模型并重写选定动作；未重写的动作回落通用实现，外部仍调用原有 `<模型编码>.<动作>` 方法 | 高 |
| FR-CRUD-11 | Java 定制写操作与通用写入共享事务；默认批量新增、删除逐条执行模型定制规则，任一记录失败整批回滚；拒绝重复、非法或不存在的模型绑定及循环调用 | 高 |

后端批量接口操作同一个模型中的业务记录。`batchCreate` 的 `records` 为 1～200 条属性键值对象；`batchDelete` 的 `records` 为 1～200 个含 `id`、`version` 的对象。默认实现沿用单条新增或删除的校验、数据范围和模型限制，全部成功后统一提交，任一条失败整批回滚。批量删除遵守模型的逻辑删除配置。该事务语义与 JSONRPC 数组中多个独立请求分别执行的语义不同。

学生模型绑定 `com.platform.custom.StudentCrudHandler`：新增前去除姓名两端空白，再执行通用新增校验与保存；其他未重写动作使用通用实现。

**list 服务请求示例：**

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "student.list",
  "params": {
    "page": 1,
    "pageSize": 20,
    "sortField": "enrollDate",
    "order": "desc",
    "filters": [
      { "field": "name", "op": "like", "value": "张" },
      { "field": "gender", "op": "eq", "value": "M" }
    ]
  }
}
```

### 4.6 视图元模型（FR-VIEW）

视图是前端页面的元数据描述，本期支持两类视图：**列表视图（list）**与**表单视图（form）**。

#### 4.6.1 列表视图（表格 + 搜索区域）

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-VIEW-01 | 列表视图定义所绑定的模型（model）、表格列（columns）、搜索区（search）、操作按钮（buttons）、分页配置 | 高 |
| FR-VIEW-02 | 表格列：绑定字段编码（field）、列标题（title）、列宽（可选）、格式化方式（可选，如日期格式、枚举显示 label） | 高 |
| FR-VIEW-03 | 搜索区：定义搜索字段（field）、匹配操作符（op）、控件类型（widget：input / select / date 等）、显示名称；渲染为表格上方的查询表单，支持查询与重置 | 高 |
| FR-VIEW-04 | 列表按钮：新增（打开表单视图）、编辑（打开表单视图并携带行数据）、删除（调用 delete 服务，需二次确认）、刷新；支持自定义按钮 | 高 |
| FR-VIEW-05 | 自定义按钮可绑定任意模型服务动作（见 4.6.3 按钮动作机制） | 高 |
| FR-VIEW-06 | 列表支持勾选记录并显示选中数量；编辑、删除及业务按钮按当前行操作，勾选状态不作为通用批量业务入参 | 中 |

#### 4.6.2 表单视图

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-VIEW-10 | 表单视图定义所绑定的模型、字段控件列表（fields）、按钮（buttons） | 高 |
| FR-VIEW-11 | 字段控件：绑定字段编码、控件类型（widget：input / textarea / number / select / radio / date / datetime / switch 等）、占位提示、栅格宽度（span）；控件类型缺省时根据字段 type 自动推断 | 高 |
| FR-VIEW-12 | 下拉/单选控件：enum 字段自动使用字段定义中的 options；ref 字段默认调用被引用模型的 list 服务加载选项 | 中 |
| FR-VIEW-13 | 表单模式：新建模式（调用 create）与编辑模式（携带主键调用 update）；编辑模式打开时先调用 read 回填数据 | 高 |
| FR-VIEW-14 | 表单按钮：保存（提交）、取消（关闭）；保存时进行前端基础校验，后端校验失败的字段级错误需回显到对应控件 | 高 |
| FR-VIEW-15 | 字段根据 editable 声明控制是否可编辑；hidden 字段不出现在表单 | 中 |

#### 4.6.3 按钮动作机制

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-ACT-01 | 按钮通过 `action` 属性声明动作，格式为 `动作类型:参数`，前端引擎据此调度 | 高 |
| FR-ACT-02 | 内置动作类型：`openForm:<视图编码>`（打开表单视图）、`service:<模型>.<动作>`（调用模型服务）、`close`（关闭弹窗） | 高 |
| FR-ACT-03 | `service` 动作支持参数来源声明：取当前行数据、取表单数据、取搜索条件或常量 | 高 |
| FR-ACT-04 | 按钮支持 confirm 提示语配置（危险操作前二次确认）、成功提示、成功后行为（刷新列表/关闭弹窗/清空表单） | 高 |
| FR-ACT-05 | 动作执行期间按钮禁用，防止重复提交；失败时展示 JSONRPC error 中的错误信息 | 中 |

### 4.8 前端引擎（FR-FE）

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-FE-01 | 启动后调用 `meta.getMenus` 动态渲染左侧导航菜单（支持多级目录、图标、排序） | 高 |
| FR-FE-02 | 点击菜单项时按视图编码调用 `meta.getViews` 获取视图定义，缓存后渲染对应视图 | 高 |
| FR-FE-03 | 列表视图渲染：搜索区（按 search.fields 渲染控件，支持查询/重置）、数据表格（按 columns 渲染）、分页器（与 list 服务的 page/pageSize 联动）、按钮区 | 高 |
| FR-FE-04 | 表单视图渲染：按 fields 渲染控件并布局（span 栅格）、必填标识、按 buttons 渲染操作按钮；以弹窗或页面形式呈现 | 高 |
| FR-FE-05 | 控件类型自动推断：无 widget 声明时按字段 type 映射默认控件（string→input、integer/decimal→number、date→date、enum→select、boolean→switch 等） | 中 |
| FR-FE-06 | 按钮动作调度：解析 action → `openForm` 打开对应表单视图；`service` 组装 params 并发起 JSONRPC 调用；执行 confirm、成功提示与刷新等后置行为 | 高 |
| FR-FE-07 | 前端基础校验：根据模型约束（required、min/max、枚举）在提交前拦截；后端字段级校验错误（error.data.fields）回显至对应控件 | 高 |
| FR-FE-08 | 统一错误提示：JSONRPC error 的 message/data 以消息框/通知形式展示 | 高 |
| FR-FE-09 | 视图定义与列表数据加载状态展示（loading）；空数据友好展示 | 中 |
| FR-FE-10 | **动态前端路由**：前端引擎依据 `meta.getMenus` 下发的菜单树动态生成前端路由表（含多级嵌套路由与 `/:id` 详情页），不得硬编码路由配置；页面刷新、元模型热更新后路由需可重建与同步 | 高 |
| FR-FE-11 | 路由守卫按菜单/按钮的 `permission` 声明控制访问；处理未知路径（404）、以及当前路由因热更新被移除时的安全跳转 | 中 |

> 说明：FR-FE-10 直接对应题目第 ③ 条"前端需要通过元模型信息，动态生成前端路由"，为本期必达项。

### 4.9 服务元模型（FR-SERVICE）

> 对应题目第 ② 条"开发者可以通过定义模型、属性、**服务**、视图"。本平台中"服务"不是引擎自动产出的固定 CRUD 动作，而是**开发者可声明的一等元模型**：通过 JSON 定义服务的参数、事务边界、动作编排与幂等策略，重载后即自动暴露为 JSONRPC 方法，全程无需编写 Java 代码。

| 编号 | 需求描述 | 优先级 |
| ---- | -------- | ------ |
| FR-SVC-01 | 支持通过 JSON 文件定义自定义服务，服务包含：唯一编码（code）、显示名称、入参声明（params）、返回声明（可选）、归属模块 | 高 |
| FR-SVC-02 | 支持 `transactional` 事务边界：多个步骤在同一事务内执行，任一步失败整体回滚，不留中间态数据 | 高 |
| FR-SVC-03 | 支持 `steps` 有序动作序列，每步声明 `call` 目标（标准 CRUD 服务 / 其他自定义服务 / 元数据服务）与 `map` 参数映射；参数来源支持入参、当前行数据、上一步返回值、常量 | 高 |
| FR-SVC-04 | 显式声明 `idempotencyKey` 的事务服务按服务编码与业务键去重；参数、调用方及权限范围一致的重复请求返回已提交结果，改变参数或范围时拒绝重放，避免重复提交或网络重试造成重复扣减 | 高 |
| FR-SVC-05 | 支持 `guards` 前置守卫（库存充足、状态允许等）与 `onError` 错误策略（rollback，事务失败时整体回滚） | 中 |
| FR-SVC-06 | JSON 服务注册后暴露为 `service.<服务编码>`；模型方法分发到该模型的 Java CRUD 处理类或通用实现，JSON 服务通过显式调用组合业务步骤，服务同名不改变模型方法绑定 | 高 |
| FR-SVC-07 | 服务定义参与元模型校验：`call` 目标存在、`map` 字段合法、无循环依赖、事务边界合法；错误定位到文件名与节点路径 | 高 |
| FR-SVC-08 | 每次调用记录操作日志（调用者、入参摘要、耗时、结果、事务 id、幂等键），支持业务追溯；记录字段、结果含义及查询权限见 FR-LOG | 中 |
| FR-SVC-09 | 视图按钮 `action` 可直接绑定自定义服务（`service:<服务编码>`），与内置动作由同一动作调度器统一调度 | 高 |

**服务定义示例（生产装配：领料）**：

```json
{
  "services": [
    {
      "code": "issueMaterial",
      "name": "生产领料",
      "transactional": true,
      "idempotencyKey": "requestId",
      "params": [
        { "name": "workOrderId", "type": "ref", "ref": "work_order", "required": true },
        { "name": "batchId",     "type": "ref", "ref": "part_batch", "required": true },
        { "name": "qty",         "type": "integer", "min": 1, "required": true }
      ],
      "guards": [
        { "call": "service.checkStockAvailable",
          "map": { "batchId": "params.batchId", "qty": "params.qty" } }
      ],
      "steps": [
        { "call": "service.deductStock",
          "map": { "batchId": "params.batchId", "qty": "params.qty" } },
        { "call": "stockMovement.create",
          "map": { "type": "ISSUE", "batchId": "params.batchId", "qty": "params.qty" } },
        { "call": "assemblyRecord.create",
          "map": { "workOrderId": "params.workOrderId", "batchId": "params.batchId" } },
        { "call": "workOrder.update",
          "map": { "id": "params.workOrderId", "status": "ASSEMBLING" } }
      ],
      "onError": "rollback"
    }
  ]
}
```

> `map` 支持路径表达式（`params.x` / `steps[i].result.x` / `const`）；嵌套的自定义服务与外层共用同一事务上下文。以此方式新增业务能力时，开发者只编写 JSON，不新增任何后端类。

### 4.10 业务场景支撑能力（FR-SCENE）

> 平台面向的是真实业务系统而非演示用 CRUD。设计原则：**每遇到一个业务上的"怎么办"，优先抽象为元模型中的一项通用能力，而不是在上层系统里硬编码 if-else**。以下能力均由平台提供，上层管理系统通过配置获得。

| 编号 | 业务场景 | 平台需提供的通用能力 | 优先级 |
| ---- | -------- | -------------------- | ------ |
| FR-SCENE-01 | 零件损坏处置、不良品流转、工单推进 | 可配置**状态机**：模型声明 `stateMachine`（初始状态、允许的 from→to 转移、守卫条件），引擎提供通用 `transition` 动作，非法转移返回业务错误码 | 高 |
| FR-SCENE-02 | 库存按质量状态分账（良品 / 待检 / 不良 / 隔离） | 通用分账维度字段 + 可用量计算规则；list 服务支持按分账维度过滤与汇总，不良品不计入可用库存 | 高 |
| FR-SCENE-03 | 整机序列号反查零件批次（追溯 / 召回） | `ref` 升级为可配置关联（1:N / N:M），支持按关联字段反向过滤、级联查询与反查清单 | 高 |
| FR-SCENE-04 | 领料不超扣、返工"补领新件 + 旧件退不良库"一增一减 | 事务编排（FR-SVC-02）+ 乐观锁 `version` 字段 + 幂等键（FR-SVC-04） | 高 |
| FR-SCENE-05 | 检验 / 返工 / 审批历史只追加不可篡改 | `appendOnly` 模型标记 + 统一操作事件流水（操作者、时间、状态前后值、原因、关联单号） | 高 |
| FR-SCENE-06 | 供应商不良率、批次直通率、返工工时看板 | `aggregate` 服务（groupBy + count / sum / avg）+ 视图支持图表组件 | 中 |
| FR-SCENE-07 | 按单据状态显示或禁用按钮、字段 | 视图元模型 `when` 条件表达式（对当前行 / 表单数据求值） | 中 |
| FR-SCENE-08 | 不同角色看到不同菜单与操作 | 菜单 / 按钮 `permission` 声明，`meta.getMenus` 与前端路由守卫按角色过滤 | 中 |

## 5. 典型使用场景

### 场景一：建模人员新增"课程"模型（目标：全程不写一行 Java/SQL/前端代码）

1. 新建 `meta/models/course.json`，定义课程模型及属性（编码、名称、学分、授课教师）；
2. 新建 `meta/views/course_list.json`，定义课程列表视图（搜索：课程名称模糊查询；表格列；新增/编辑/删除按钮）与课程表单视图；
3. 编辑 `meta/menus/main.json`，在"基础数据"目录下添加"课程管理"菜单项，指向 `course_list` 视图；
4. 调用 `meta.reload`（或管理界面触发重载）；
5. 元模型引擎校验通过后注册：数据库自动生成 `t_course` 表、`course.*` 服务立即可用；
6. 业务用户刷新页面，"课程管理"菜单出现，即可进行课程的增删改查。

**验收要点**：以上过程无需修改任何后端 Java 代码与前端页面代码；校验失败时（如视图引用了不存在的模型）给出明确错误且不影响既有功能。

### 场景二：业务用户日常操作

1. 打开系统，左侧菜单由元数据渲染生成；
2. 点击"学生管理"，表格自动加载 `student.list` 数据，展示姓名、性别、年龄、入学日期列；
3. 在搜索区输入姓名关键字"张"，点击查询，表格刷新为过滤结果；
4. 点击"新增"，弹出学生表单；填写后点击"保存"，前端校验通过后调用 `student.create`；若后端校验失败（如姓名为空），错误回显到姓名控件；
5. 勾选一条记录点击"删除"，出现确认框，确认后调用 `student.delete`，列表刷新且记录消失。

### 场景三：生产装配系统中的异常流（零件损坏处理）

> 用于验证平台能否支撑真实生产细节，而不是只能生成 CRUD 页面。以下每一步都应通过元模型配置 + 平台通用能力实现，不在上层系统硬编码业务逻辑。

1. **来料检验发现损坏**：检验员在 IQC 视图登记不良记录（零件、批次、数量、不良代码、发现工位、责任人、凭证附件），该模型标记为 `appendOnly`；
2. **库存分账与隔离**：库存模型按 `qualityStatus`（待检 / 合格 / 不良 / 隔离）分账，损坏件移入隔离库位；可用量计算规则自动排除不良与隔离数量，后续领料守卫据此拒绝超领；
3. **处置决策**：通过状态机从"待处置"流转到"退货 / 报废 / 让步接收 / 返修复检"，每次流转写入事件流水（操作者、前后状态、原因、审批人），历史不可修改；
4. **追溯反查**：若损坏件已装机，按 `assemblyRecord`（整机 SN ↔ 零件批次/序列号）关联反查受影响整机清单，并冻结对应工单；
5. **返工事务**：自定义服务 `service.rework` 在同一事务内完成"补领良品 → 旧件退回不良库 → 生成返工记录 → 工单状态回退 → 复检登记"，任一步失败整体回滚；`requestId` 保证同一业务请求的网络重试不重复扣减；
6. **复检与放行**：复检合格并关闭全部相关未结异常后，整机和工单解除冻结；复检失败时继续返工，保留检验、状态和追溯记录；
7. **统计看板**：`aggregate` 服务按供应商 / 批次 / 不良代码汇总不良率、直通率与返工工时，由视图图表组件渲染。

**并发与一致性要求**：两名检验员同时登记同一批次不良时，数量不得超出该批次总量（`version` 乐观锁）；同一领料请求重复提交不得重复扣减；事务中任一步失败不得留下脏数据。

**验收要点**：整条异常链路无需修改后端 Java 代码与前端页面代码，全部由模型 / 服务 / 视图 JSON 配置 + 热重载获得；演示数据预置若干不良品、返工单与追溯链，页面首屏即可看到异常场景而非空表。

## 8. 约束与假设

**约束：**

1. 后端使用 Java 17 与 Spring Boot；元数据和业务接口使用 JSONRPC 2.0，账号会话、附件和日志平台接口使用受会话保护的 REST；
2. 建模方式为本期仅支持 JSON 文件编辑 + 热重载，不提供可视化建模界面；
3. 业务数据存储于关系型数据库，模型与物理表一一对应。

**假设：**

1. 建模人员具备 JSON 编写能力，并遵循平台元模型规范；
2. 单体部署即可满足本期并发要求，无需分布式；
3. 权限采用按应用授权与继承式数据范围，不包含多租户、部门组织及多人共享授权。

| AC-11 | 开发者仅通过新增/修改 JSON 定义一个自定义服务（含事务步骤、前置守卫、幂等键），重载后即可通过 JSONRPC 调用，全程零 Java 代码改动 |
| AC-12 | 前端路由完全由菜单元模型动态生成：新增菜单项后刷新页面自动出现对应路由与页面；热更新删除菜单后旧路由被移除且当前页安全跳转 |
| AC-13 | 生产装配场景零件损坏闭环可运行：不良登记 → 隔离分账 → 序列号追溯反查受影响整机 → 返工事务（补领 + 退旧 + 复检）→ 状态流转历史 → 不良率看板，且全部通过元模型配置实现 |
| AC-14 | 并发领料不发生超扣；声明幂等键的业务服务重复提交或网络重试不重复扣减；模型批量新增、删除任一条失败时整批回滚且不留脏数据 |

| AC-15 | 用户创建、首次改密、重置密码、停用及用户逻辑删除正确；删除后既有会话失效，管理员和当前登录账号的删除被拒绝，历史业务记录保留 |
| AC-16 | 应用访问、编辑和业务操作授权在同一角色页面配置；隐藏应用的接口不能被直接越权访问，多角色按并集合并，角色删除遵守引用约束 |
| AC-17 | 本人及所属记录在列表、详情、关联和统计接口中保持一致，其他账号不能读取对应工单、整机及其检验记录；共享资料按模型规则可见 |
| AC-18 | 附件上传、下载、移除及大小/数量限制正确，记录归属和应用授权生效，文件不通过静态目录公开 |
| AC-19 | BOM 发布后不可随意修改，按 BOM 建单固定版本；装机、齐套和初装核销拒绝错件、错位、超数量和跨单领料 |
| AC-20 | 未用领料余额与余料退库一致；超额退库、重复提交和中途失败均不导致库存或流水重复变更 |
| AC-21 | 图表由元数据驱动并跟随筛选，首次不通过、复检通过的整机仍计首次未通过；无记录时不产生错误比例，数据范围隔离生效 |
| AC-22 | 成功、失败、幂等重放及嵌套回滚日志具有正确操作人、根调用及事务关联；日志查询需管理权限，参数原文不落库 |
| AC-23 | 为指定模型注册 Java CRUD 处理类后，原模型接口及服务内调用执行定制逻辑，其他模型和未重写动作使用通用实现；通用保存后异常及批量中途异常均完整回滚，权限拒绝发生在处理类执行前 |

## 10. 风险与应对

| 风险 | 影响 | 应对措施 |
| ---- | ---- | -------- |
| 元模型错误导致运行异常 | 服务不可用 | 严格的启动/热更新双阶段校验；热更新失败回退旧版本 |
| 动态 SQL 拼装引入注入风险 | 数据安全 | 字段/操作符/排序白名单机制 + 全参数化 + 专项安全测试 |
| 自动变更表结构误删数据 | 数据丢失 | 仅自动新增列，破坏性变更仅告警不执行 |
| 前端控件与元数据表达能力不匹配 | 页面渲染失败 | 控件类型与字段类型映射矩阵明确化；元数据校验阶段拦截不支持的组合 |
| 热更新期间请求一致性 | 脏数据 | 元模型仓库整体原子替换（快照切换） |
